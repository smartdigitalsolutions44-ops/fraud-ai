## How the manifest was produced

From a clean checkout of the tagged commit, on a freshly built Demo world:

```bash
AUDIT_ANCHOR_DIRECTORY=/srv/sentinel-demo/anchors \
  fraud-ai audit anchor-now --always                # anchor the audit chain head
OPERATOR_ID=sec fraud-ai release manifest --out release/v0.15.0-rc1.json \
    --sbom sbom/fraud-ai.cdx.json --operator-key data/demo/keys/operator-sec.pem
fraud-ai release verify release/v0.15.0-rc1.json --sbom sbom/fraud-ai.cdx.json
```

(with the Demo world's `demo.env` loaded, and `AUDIT_ANCHOR_DIRECTORY` set to a neutral path so
the signed manifest records no local file-system path). It records the commit, the migration revision,
the API, package, feature and sequence versions, the active policy and its definition hash,
each deployed model's digest and signature, the SBOM hash and the newest audit anchor.

## What this manifest does *not* prove (stated, not hidden)

* **It is signed with the Demo world's release key**, generated by `fraud-ai demo reset`,
  not by the Vault transit key used for `v0.12.0-rc1` on the staging stack. The signer was
  the demo's authenticated `security_admin` operator `sec`. The staging stack (Vault, Object
  Lock, the signed image) needs Docker, which was not available where this release was cut.
* **No image evidence.** The manifest carries no image digest or cosign evidence. The
  container image for this commit was built, signed (SLSA provenance and CycloneDX SBOM
  attestations), verified, and a tampered copy refused, in the CI `container` job of the run
  above; that evidence lives in CI, not in this manifest. `release verify` reports the image
  checks as skipped, never as passed.
* **Model artefacts and the audit anchor belong to that Demo world.** They can be
  re-verified only against the same world; a new `demo reset` creates new keys.
